## ADDED Requirements

### Requirement: ProviderWire V4 unary fixture provenance and raw transport oracle

The conformance tooling SHALL inventory every provider-backed unary fixture eligible for ProviderWire V4 evidence. Eligibility SHALL require an unchanged real-provider recording or byte-identical matching registered-upstream input with its existing provenance and request expectation. The tooling SHALL initially select only the registered Bedrock unary fixture and SHALL record other providers as a coverage gap until provenance-valid unary inputs exist.

For each selected fixture, the exact registered TypeScript provider package SHALL replay the existing input and produce the raw `LanguageModelV4GenerateResult`. A non-mutating check SHALL validate the complete raw result against the ProviderWire V4 generate-result schema, transport it as unary JSON through the exact pinned Gateway client, and compare the consumed semantic outcome with the fixture's existing `expected-generate.json` oracle.

Raw result values and ProviderWire response bytes SHALL be classified as derived transport projections rather than provider inputs, provider recordings, private-server evidence, or host-policy output. The tooling MUST NOT rewrite, truncate, splice, synthesize, or reclassify `input.response.json` or any provider request/response input to expand coverage.

#### Scenario: Eligible unary fixture is replayed unchanged
- **WHEN** the ProviderWire V4 unary conformance check selects the registered Bedrock generate fixture
- **THEN** it SHALL replay the fixture's unchanged provider input through the exact registered TypeScript provider and validate the resulting complete raw generate result

#### Scenario: Raw Gateway transport preserves the existing oracle
- **WHEN** the raw schema-valid result is served as ProviderWire unary JSON to the pinned stock Gateway client
- **THEN** the client's consumed semantic content, finish reason, usage, warnings, and applicable metadata SHALL match the existing unary expectation before host policy

#### Scenario: Missing provider unary evidence remains a gap
- **WHEN** another provider lacks a real recorded or matching registered-upstream unary input
- **THEN** the conformance inventory SHALL report that bounded provider coverage gap and SHALL not substitute a synthetic input

#### Scenario: Provider inputs retain provenance
- **WHEN** raw or normalized ProviderWire projections are generated or verified
- **THEN** every provider `input.response.json` or other provider input SHALL remain byte-unchanged and in its original provenance category

#### Scenario: Raw transport claim remains narrow
- **WHEN** raw unary evidence passes
- **THEN** the repository SHALL claim pinned provider-output and Gateway-client transport preservation only, not Vercel private-server acceptance, host-policy behavior, or Go handler correctness

### Requirement: Independent unary policy oracle and real handler lane

The conformance tooling SHALL define a TypeScript unary policy projector independent of the Go V4 runtime. For a selected raw generate result, the projector SHALL remove exactly the fields prohibited by the H2 response policy: top-level and per-content provider metadata, raw usage, request metadata/body, response headers/body, provider identity, and backend model ID. It SHALL preserve the safe response ID/timestamp and all other contract-valid fields.

The projector SHALL produce the policy-normalized ProviderWire expectation required by the Go-only runtime test and SHALL record its source fixture, registered baseline authority, policy profile, and generation command. The normalized expectation SHALL be schema-valid before replacement and MUST NOT be generated by the Go V4 handler or its response adapter.

The Go conformance lane SHALL place the real provider for the same unchanged unary fixture behind the real V4 handler and SHALL compare the handler's result with the independently normalized expectation. When policy has no observable effect, the lane MAY reuse the raw expectation only after proving semantic equality. The lane SHALL also verify request adaptation reaches the provider and resolver and `DoGenerate` invocation counts are exactly one.

#### Scenario: Policy projector removes only prohibited fields
- **WHEN** a raw unary result contains provider metadata, raw usage, request details, response headers/body, provider identity, or backend model ID
- **THEN** the independent projector SHALL omit those fields and preserve every other contract-valid semantic field

#### Scenario: Normalized expectation has independent authority
- **WHEN** a policy-normalized expectation is generated or updated
- **THEN** its provenance metadata SHALL identify the raw source fixture, registered package baseline, fixed H2 policy profile, and TypeScript generation authority
- **AND** no Go handler, Go response adapter, or Go runtime output SHALL participate in generating it

#### Scenario: Real handler matches normalized expectation
- **WHEN** the Go provider replays the selected unchanged unary input behind the real V4 handler
- **THEN** the handler's complete JSON result SHALL match the independently generated policy-normalized expectation semantically

#### Scenario: Request reaches provider once
- **WHEN** the selected fixture request passes V4 validation and policy
- **THEN** the handler resolver and real provider `DoGenerate` path SHALL each run once
- **AND** the downstream provider request SHALL continue to match its existing `expected-requests.jsonl`

#### Scenario: Policy-changing output is not compared with raw output
- **WHEN** H2 policy removes an observable field from the raw provider result
- **THEN** the real handler SHALL be compared with the normalized expectation rather than the unfiltered raw expectation

#### Scenario: Normal verification is non-mutating
- **WHEN** ProviderWire V4 unary conformance runs through the aggregate check
- **THEN** it SHALL regenerate raw and normalized values in memory or temporary storage and compare them without changing committed files
