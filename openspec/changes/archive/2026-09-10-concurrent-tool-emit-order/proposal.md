## Why

`openspec/specs/concurrent-tool-execution/spec.md:70` requires each tool goroutine to emit its `StreamToolResult` or `StreamToolError` as the tool completes, in completion order. The implementation instead waits for every tool in the step and then emits in tool call order (`streamtext.go:1650-1659`, and again on the approval-resume path at `:2001-2005`), so no tool result reaches the consumer until the slowest tool finishes.

Upstream `ai@7.0.65` at the registered baseline `d76eb85a` emits per tool: `execute-tools-from-stream.ts:229` enqueues inside each per-tool `async` callback, and call order is restored later and only for the provider messages by `sortToolResultContentByToolCallOrder` (`to-response-messages.ts:222-257`). The Go comment at `streamtext.go:1451-1453` claims declaration-order emission matches upstream, which is the opposite of what upstream does.

One loop is currently doing two jobs. `spec.md:84` separately requires `step.ToolResults` in call order, and satisfying that by waiting is what makes the stream violate `:70`. See #161.

## What Changes

- `executeSingleTool` emits each tool's stream event from that tool's own goroutine, as it completes.
- Both call sites keep a post-`Wait` loop that builds `step.ToolResults` in tool call order, so `spec.md:84` continues to hold. On the approval-resume path that loop also continues to build `approvedToolParts` for the provider message.
- `CompareChunks` sorts each maximal run of adjacent locally-executed `tool-output-available` and `tool-output-error` chunks by `toolCallId` before comparing. Chunks marked `providerExecuted` are excluded and end a run, since their order comes off the recorded wire. Concurrent emission makes the relative order of those chunks non-deterministic, and the recorded fixtures cannot express the distinction: they are generated by running upstream `streamText` with tool bodies that resolve immediately, and the fixture config schema has no delay field.
- The comment at `streamtext.go:1451-1453` is corrected, as is the resume-path comment that made the same claim.
- A dedicated `emitMu` holds the emit and the `OnChunk` callback together, so `OnChunk` stays serial and in stream order as it is upstream.

## Capabilities

### New Capabilities
- None

### Modified Capabilities
- `conformance-testing`: chunk comparison becomes order-insensitive within a run of adjacent locally-executed tool output chunks, and stays strict everywhere else.

## Impact

- `streamtext.go`: emission moves into the tool goroutine at both call sites. Public API unchanged.
- `test/conformance/runner.go`: `CompareChunks` normalizes before comparing.
- `streamtext_test.go`: `stream_events_arrive_in_declaration_order` becomes `stream_events_arrive_in_completion_order` and asserts the spec's scenario.
- No wire format change. `step.ToolResults`, `step.ToolCalls` and the provider messages are byte-identical.
- Behavior change visible to consumers of `FullStream()`: tool results now arrive as each tool completes rather than batched. Time to first result changes from the slowest tool's duration to the fastest.
- `OnChunk` keeps its existing contract. It is still invoked serially and in stream order, which is what upstream does at `stream-text.ts:1196`. Without the lock it would have become concurrent, which raced and reordered.
- Emission has no cancellation path, so a consumer that abandons `FullStream()` now strands one goroutine per tool rather than one in total. Pre-existing, amplified here, and filed separately.
- Go resolves ties nondeterministically where upstream, being single-threaded with uniform microtask depth, resolves them in call order. Recorded as an intentional deviation in `upstream.yaml` and `PARITY.md`.
- End-to-end turn latency is unchanged, because the next model call still needs every result.
