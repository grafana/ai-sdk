## Context

The registered baseline is `@ai-sdk/openai` 4.0.71 at `08ae5ad05bc12496dd1ffcf64e34419e0831300d`. Its `normalize-openai-json-schema.ts` and tests remove string-schema `propertyNames` and emit one compatibility warning per affected schema, reject non-string/boolean forms, recursively visit schema-bearing JSON Schema 7 keywords, and preserve the caller's schema. The Responses language model normalizes structured output, and `openai-responses-prepare-tools.ts` normalizes both function input and optional output schemas. This is a provider implementation gap (the provider-adapter row in `test/conformance/PARITY.md` is mixed), not a pinned-version upgrade.

In Go, `buildParamsForProvider` in `providers/openai/convert_request.go` builds the request before both `model.DoGenerate` and `model.DoStream` initiate HTTP. `applyResponseFormat` in `providers/openai/apply_options.go` and `functionToolParam` in `providers/openai/prepare_tools.go` currently decode caller-provided `json.RawMessage` directly to request maps; the latter also feeds `namespaceFunctionTool`. Existing helper signatures do not propagate response-format warnings/errors or function-schema errors. The public `provider.Warning` already supports `WarnCompatibility`.

## Goals / Non-Goals

**Goals:** Apply the pinned upstream schema transformation to JSON response formats and regular/namespaced function-tool input and optional output schemas, with identical preflight behavior in generate and stream calls. Preserve unrelated schema content, caller-owned raw JSON, and strict/name/description semantics.

**Non-Goals:** Change the generic Go schema generator, non-OpenAI providers, provider/tool public interfaces, `json_object` handling, tool result serialization, OpenAI acceptance of otherwise unsupported JSON Schema keywords, or frontend wire data. This proposal does not alter baseline pins or claim a live provider recording.

## Decisions

1. **Use one provider-private normalizer at the request conversion boundary.** Parse each supplied JSON schema into a fresh JSON value, recursively process schema nodes, then return the normalized value, compatibility warnings, and error. Visit `properties`, `patternProperties`, `definitions`, `$defs` record values; `additionalProperties`, `additionalItems`, `contains`, `not`, `if`, `then`, `else`; `items` (single schema or schema array); `allOf`, `anyOf`, `oneOf` arrays; and schema-valued `dependencies` (leave string-array dependencies unchanged). Preserve boolean schema definitions and other keywords including `required` and `additionalProperties: false`. Do not traverse arbitrary non-schema fields or resolve `$ref`. For `propertyNames` with `type: "string"`, remove the keyword and emit a single `provider.WarnCompatibility` per affected input schema (feature `JSON Schema propertyNames`, upstream details text). If `propertyNames` is boolean or has a type other than `string`, return a contextual provider error before HTTP; a null value follows upstream's absent-value behavior and is removed without a warning. This matches the pinned normalizer instead of imposing general strict JSON Schema rules. An alternative of transforming all nested maps indiscriminately would alter data keywords; it is rejected.

2. **Propagate normalization outcomes from both request branches.** Change `applyResponseFormat` to return warnings/error and append its warnings in `buildParamsForProvider` before tool warnings. Change `functionToolParam` and its normal and namespace callers to return warnings/error, including optional `OpenAIToolOptions.OutputSchema` warnings after the input schema warning. `prepareTools` already returns warnings/error and threads through `buildParamsForProvider`. Treat explicit JSON `null` in the optional response and tool output schema positions as absent, as in the pinned upstream, while retaining invalid-root rejection for supplied function input schemas. Reject malformed JSON during decoding instead of silently forwarding an unusable nil map. This is a Go input-decoding adaptation for caller-supplied `json.RawMessage`, not an additional JSON Schema validation rule: upstream receives already-parsed `JSONSchema7` objects. The existing build-before-HTTP path supplies the same failure/warning behavior to `DoGenerate` and `DoStream`, including `StrictJSONSchema == false` (which only sets the API's strict flag). Avoid a second model-level normalization path or SDK mutation. These helper signature changes are private to `providers/openai`.

3. **Use deterministic local provider-boundary proof first.** Add normalizer tests based on the registered upstream normalization cases, covering recursive keywords, boolean definitions, per-schema warning cardinality, null removal without warning, non-string/boolean rejection, and original JSON unchanged. Cover malformed response, input, and optional output schema JSON with focused local-error tests asserting no HTTP requests. Add request-capture and no-request tests in `providers/openai` exercising structured output, regular and namespaced function input/output schemas, strict true/false, and both generate and stream through `buildParams`. Check `test/conformance/openai/` for authentic recordings or matching upstream fixtures before adding any conformance input; never hand-author a `recorded/` or `upstream/` input. If no authentic fixture covers this case, keep synthetic transport behavior in focused tests and explicitly retain the live-provider coverage gap. An alternative of fabricating provider events to create snapshots would violate fixture provenance.

## Risks / Trade-offs

- **Unsupported constraints cease to be enforced server-side** → Emit the upstream compatibility warning and retain callers' untouched schemas for independent client-side validation; do not claim OpenAI validates removed constraints.
- **JSON Schema supports many constructs** → Match the pinned traversal precisely; preserve unlisted fields instead of speculatively rewriting them, and test both boolean schema and schema-valued branches.
- **Failure/warning ordering can differ across entrypoints** → Centralize in `buildParamsForProvider` and assert no HTTP call for invalid combinations on both `DoGenerate` and `DoStream`.
- **No authentic input fixture may exist for this boundary** → Focused request tests are the regression contract but not evidence of live API acceptance; only update conformance snapshots when provenance is valid.

## Migration Plan

No migration is required: request preparation changes only within the OpenAI provider. Implement and validate as one independently green provider package against the existing published module baseline; retain previous behavior by reverting this provider change if necessary. At implementation time, run focused `providers/openai` tests, `mise run parity-check` for parity-sensitive behavior, and module-resolution checks as relevant. No published dependency change is planned.
