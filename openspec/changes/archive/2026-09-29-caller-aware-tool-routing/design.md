## Context

The registered reference is Vercel AI SDK `ai@7.0.109` (`4e8c387622ee1bb0d55841664416d38754d5c9a3`); the issue's `ai@7.0.107` caller/result files are behaviorally unchanged. Its `tool-caller-configuration.ts` validates a tool-to-callers mapping once, then prepares `executionTools`, `modelTools`, and optional user messages per step. Its `execute-tool.ts` converts an async iterable into preliminary outputs followed by a final repetition of the last output. `stream-text.ts` excludes preliminary outputs from final result collections and continuation. `generate-text.ts` has a separate path; Go's `GenerateText` consumes `StreamText`, so both Go entry points should share the same implementation.

Go currently converts `cfg.tools` into provider tools, filters only that list by active names, and then uses `cfg.tools` for validation, approval, and execution. `Tool.Execute` returns a single `(json.RawMessage, error)`; provider preliminary results and the UI `preliminary` field already exist. The OpenAI/Anthropic provider adapters already pass typed per-tool `allowedCallers` and caller metadata through their provider contracts. The work must honor provider-independent conformance provenance and existing approval/concurrency semantics.

## Goals / Non-Goals

**Goals:** Match the registered upstream's opt-in tool caller visibility, local binding, provider-option preparation, and async-iterable preliminary/final output behavior. Preserve existing behavior without caller configuration or streaming execution. Cover initial calls, active tools, approval resumes, cancellation, and continuation.

**Non-Goals:** A JavaScript sandbox, implicit sandbox-provider integration, a new Go security policy that rejects emitted tool calls based on provider caller metadata, replacing existing provider adapters, or a generics-based translation of TypeScript compile-time inference.

## Decisions

1. **Opt-in caller configuration and tool definitions.** Offer a call-level mapping of callee names to ordered allowed caller names, with a named direct-call sentinel, alongside opt-in local/provider caller definitions associated with a `Tool`. Reject references to unknown tools or to names not defined as caller tools when the configured tool set exists. A missing caller mapping retains current direct visibility; an explicit empty list hides that callee. Keep the policy at the orchestration layer rather than adding an `ExecutionOnly` boolean: a tool can be visible to a provider caller yet hidden from direct model invocation. This follows upstream's tool caller definition and map; Go APIs need not mimic TypeScript generics.

2. **Prepare separate per-step sets.** Resolve the mapping against the full tool set, then filter active tools for the current step before producing independent model and execution copies. Start both from the filtered set. For every configured callee, retain it in the model set if direct or provider-routed; otherwise remove it from model exposure, while retaining it in the execution set. The execution set supplies parser/approval/executor lookups for the step; the model set supplies provider tools and `ToolChoice`. This includes named choice visibility and step overrides. Upstream execution looks up calls in the execution set without re-verifying the caller identity; do not introduce a new Go-only authorization check. Caller routing is an exposure/binding mechanism, not a security boundary against forged provider output.

3. **Local and provider caller binding.** For a local caller, pass only its active, configured callees into its bind callback and use the bound tool for execution. With no model-message callback, expose the bound caller definition to the model; with a callback, retain the unbound caller definition and append the returned defined string (including an empty string) as a user message after the current step messages (deduplicating identical text already in the latest user text or another announcement). For a provider caller, invoke its preparation callback on the callee's provider options in caller-list order; the callee stays model-visible, even if direct access is not configured. Leave manually supplied provider options untouched if no callback is configured; allow the callback to define its own merge/override behavior, just as upstream does. The SDK does not itself mutate supplied options, but a callback owns any mutation it makes to values it receives. No generic rejection of manual `allowedCallers` or provider-specific automatic inference from arbitrary names.

4. **Local streaming tool outputs.** Add an optional streaming execution path alongside the existing `Tool.Execute`, modeled as a synchronous Go producer accepting `context.Context`, input/options, and an emission callback. It emits zero or more values; each is a preliminary result. On successful return, repeat its last yielded value as the final output (or the absent value for an empty producer), matching upstream async iteration. A single-result `Execute` produces only a final result. Do not allow both callbacks on one tool; validate ambiguous configuration before execution. Callback delivery is serialized through the orchestration event loop so multiple tool goroutines cannot invoke `OnChunk` concurrently. Producer return/error, canceled context, and final-output conversion terminate each tool independently; cancellation is passed through the context and emission stops on cancellation. Preliminary results carry the existing stream/UI `Preliminary` marker, but only the final result is recorded in `ToolResults`, passed to `ToModelOutput`, considered by completion/continuation, or reported as the tool's terminal callback. Keeping the callback internal to the execution lifetime avoids channel lifetime/close ownership; unlike TypeScript's async iterable, this is a Go-idiomatic shape with matching observable results.

5. **Approval and generate ownership.** Approval-required tools do not begin execution until approved. For approved local calls on initial and resumed paths, emit preliminary results to the stream as they arrive; append only the final result to the model prompt. Provider-executed results continue through the provider stream and are never re-executed locally. `GenerateText` and Agent delegation inherit the routing and final-only result collections through `StreamText`; `GenerateText` need not expose a separate preliminary output list. Maintain the existing `stop`/`tool-calls` execution eligibility, independent errors, and step completion behavior.

6. **Parity proof.** Use upstream `stream-text.test.ts` local-caller, provider-caller, and preliminary-result tests and the registered version's tool execution helpers as the reference; add Go provider-call capture and core/UI tests first. For UI-visible changes, add a provider-independent UI fixture and schema-parsed frontend integration scenario. Never fabricate a provider `recorded/` or `upstream/` input; use focused tests for synthetic calls. Run `mise run parity-check` on committed parity behavior. Keep provider adapter changes limited to evidence of an actual missing mapping.

## Risks / Trade-offs

- **Exposure is not authorization:** A provider that emits the name of a hidden-but-executable tool could still trigger execution, as in the upstream implementation. Document this limit rather than asserting that upstream enforces caller identity; do not add a Go-specific guard under an upstream-matching change.
- **Go callback versus async iterable:** The Go callback is pull-synchronous and must serialize UI emission without blocking unrelated tool completion; tests should exercise slow consumers, cancellation, and interleaving. An empty stream's undefined upstream final requires an absent/nil output representation, not an invented JSON value.
- **Provider-specific options:** Manual values may conflict with prepared ones. Mirroring the provider caller's callback semantics avoids a generic silent merge rule; assert both passthrough and explicit callback behavior in tests.
- **Active filtering and approval resume:** Upstream approves saved calls using the original tool set before the new step's active filtering. Keep resume execution distinct from per-step visibility and test this boundary rather than assuming the current active set governs historical approvals.

## Migration Plan

The feature is opt-in. Add the APIs and tests without changing existing tool behavior when callers and streaming execution are unset. Consumers can adopt caller routing and streamed results incrementally; rollback is removing the opt-in configuration. No new provider dependency or wire protocol is needed.

## Open Questions

No product decision is pending for this proposal: upstream behavior is the approved reference. During implementation, confirm the exact Go public names and the representation of an absent final JSON output against existing API/serialization conventions; neither should change the specified behavior.
