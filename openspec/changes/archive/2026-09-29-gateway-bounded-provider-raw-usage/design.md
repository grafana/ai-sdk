## Context

`provider.Usage.Raw` is `json.RawMessage` and direct provider conformance usage goldens already contain Anthropic-native objects. `ai-gateway/providerwire/v4/response.go` and `stream.go` map only known counters; `providers/grafana/model.go` filters unknown usage members. Strict private response schemas reject `usage.raw`. Verified with `git -C ~/src/ai show 4e8c387622ee1bb0d55841664416d38754d5c9a3:packages/provider/src/language-model/v4/language-model-v4-usage.ts` and the same Git object's `packages/gateway/src/gateway-language-model.ts` (no shared checkout modifications): the registered `@ai-sdk/provider@4.0.17` defines optional `raw?: JSONObject`; the registered `@ai-sdk/gateway@4.0.88` client passes unary parsed response and streaming finish through while filtering only distinct `type: "raw"` stream parts. Pinned Gateway tests cover pass-through usage but do not define private-service response policy; this proposal defines the local authenticated ProviderWire dialect, not private Vercel service behavior. PARITY.md lists Gateway runtime/Go client and LanguageModelV4 as mixed; request projection does not prove response safety.

## Goals / Non-Goals

**Goals:** Preserve optional raw provider usage on supported unary and streaming finish responses and through the Go client; keep strict schemas, count validation, bounded memory/bytes, safe failure framing, and privacy of all unrelated fields. Supply direct, two-client, and non-propagation regression evidence.

**Non-Goals:** Changes to `provider.Usage`, normalized billing, provider fixtures/usage goldens, request projection, UI chunks, backend routing, generic provider metadata, streaming `type: "raw"` handling, or untrusted/public unauthenticated discovery. No claim about Vercel's private Gateway service.

## Decisions

1. **Authenticated raw usage is an opaque object, not a field-filtered subset.** An absent (`nil`/zero-length) provider `Raw` omits `usage.raw`; any nonempty supplied `Raw` must be a single valid JSON object (including `{}`), with null/scalars/arrays/empty whitespace invalid. Both server and Go client reject invalid UTF-8 bytes and unpaired escaped UTF-16 surrogates (including in nested string keys and values); valid high/low surrogate escape pairs are accepted. Validate the original size-limited JSON bytes before Go JSON decoding/encoding can replace invalid Unicode with U+FFFD. Preserve keys and values, including provider-native nested token breakdown, `service_tier`, and `inference_geo`, under `usage.raw`; do not canonicalize keys, merge into normalized fields, or scan for hypothetical sensitive key names. Alternative reviewed subset discards legitimately unknown accounting fields and has no stable public provider-native allowlist. Authorization to the model response is the disclosure boundary: do not add credentials, headers, backend IDs, request/response data or other provider metadata outside the validated raw object. Raw may itself contain arbitrary provider-supplied values, so it must not be used by Gateway-owned logging, telemetry or billing. An explicit JSON `null` is *invalid*, not absent, to avoid silent loss of supplied data.

2. **Bound before parse and before marshal; reuse existing configurable envelopes.** Use a shared maximum of **1 MiB (1,048,576 bytes) of raw JSON input**, counted before trimming, parsing, or copying, also constrained by the applicable configured `UnaryResponseBytes` or `StreamFrameBytes` (the latter includes `data: ` and `\n\n`). The 1 MiB ceiling matches the current default complete-frame limit and prevents the larger default 8 MiB unary envelope from becoming the raw-object ceiling; no new configuration surface. Shorter configured limits remain authoritative. Check raw length alongside existing unary aggregate preflight or stream-finish preflight before JSON validation/any marshal, validate one complete object document and its Unicode, then encode with standard `json.RawMessage` in the minimal DTO and check entire encoded unary body/complete frame limit (escaping may enlarge bytes). Never decode raw into an unbounded map solely to inspect keys; all validation/encoding allocations must be bounded by a constant multiple of the configured envelope. StreamParts × StreamFrameBytes already bounds aggregate server response from represented parts (reason with overflow-safe arithmetic, not an eagerly allocated product); the client already enforces cumulative StreamBytes, event bytes and count. Go client first applies existing bounded full-unary and complete-event reads, then preserves the existing `validJSON` guards on complete original unary bytes (`readJSON`, before `decodeGenerate`) and stream events to validate UTF-8 and escaped surrogate pairs before Go normalization; test both guards for raw usage. `decodeFields` and `wireUsage.UnmarshalJSON` currently copy bytes into intermediate maps: those copies are bounded by the full response/event envelope, not avoided. Check present raw length against 1 MiB and the applicable configured `UnaryBytes`/`StreamEventBytes` before retaining it in `provider.Usage.Raw`, validate it as one object, and keep intermediate copies bounded by existing full-envelope limits; do not claim a pre-copy check without a pre-decode scanner. On Go client's decoded response, exact byte-for-byte formatting is not a protocol promise: JSON object semantics and field values are. Alternative relying only on full-response limits would allow expensive validation of raw fields before validation and up to 8 MiB in a unary response.

3. **Reject bad supplied raw atomically at the representation boundary.** Unary mapping/encoding failure yields the existing fixed internal-error HTTP document before success headers; streaming finish validation/encoding failure writes no finish and attempts the existing single bounded terminal internal-error SSE frame after commitment, unless writer failure prevents another write. No normalized-only success fallback, partial frame, reflected raw body, or provider error detail. Other normalized usage counts still require nonnegative JavaScript-safe integers, regardless of raw. Go client rejects hostile-server malformed/oversized raw as bounded non-retryable protocol failure (no partial unary result; stream at most one terminal `PartError`), not as silent omission. Unknown unrelated server-owned usage members retain existing filtering.

4. **Keep trust domains distinct.** Adapt exact private `unary_success.json` and `stream_event.json` schemas with optional object `usage.raw` (arbitrary nested valid JSON); preserve strict root/usage `additionalProperties: false`. Existing tests asserting raw usage omission must change only that assertion; provider-private metadata elsewhere must remain omitted. `ai-gateway/cmd/grafana-ai-gateway/internal/service/model_observability.go` already filters provider raw usage metadata from metadata-only exports; verify this boundary with a non-propagation test instead of extending observability payloads. `middleware/prometheus` disallows raw usage labels. Registered TypeScript client should preserve supplied usage but server raw HTTP/schema tests are authoritative for safety it does not enforce.

## Risks / Trade-offs

- [Provider puts sensitive data inside its usage object] → Authenticated-only response policy and bounded size; preserve caller-visible raw exactly as direct SDK does, never send to Gateway telemetry/logs/metrics or reveal it in errors. A demonstrated provider secret in native usage requires a separately reviewed policy change, not a silent heuristic filter.
- [JSON escaping or whitespace defeats apparent size limits] → Count original bytes before validation, apply final encoded-body/frame limit and client event/cumulative limits, exercise exact/one-byte and escaped values in tests.
- [Both clients differ on hostile server input] → Registered TS client is permissive by design; local Go client intentionally enforces stricter object/bounds consistent with the strict server. Differential parity requires valid responses; hostile server tests assert Go safety, not identical TS failures.
- [Existing privacy tests previously used raw usage as a canary] → Separate deliberately allowed raw canary from forbidden provider metadata/backend/header canaries and assert only the latter cannot escape except in user/provider-authored raw content.

## Migration Plan

Add server validation/DTO/schemas and Go decoder in the same change; update current omission assertions and add raw-positive and raw-negative HTTP/client tests. First establish deterministic two-client Gateway streaming replay from the unchanged recorded Anthropic chunks (the current `ai-gateway/test/providerwire-v4/testserver` registers fake models only); these streaming inputs do not provide unary response evidence. Cover Gateway unary with separate deterministic synthetic/focused tests, without deriving unary responses from recorded streams. Do not present `mise run test-providerwire-v4` as running the recorded streaming matrix until replay is wired. If the #201 replay harness is unavailable, mark its completion a prerequisite to recorded-fixture acceptance, not an already passing test. Run direct and two-client recorded streaming fixture tests without changing goldens once replay exists, then parity baseline checks. Rollback restores prior server omission and client filtering together; no stored data migration or protocol version bump, because `usage.raw` is an optional additive field to the same v4 response family.

## Open Questions

None blocking this proposal. If security review finds an actual native provider usage key carrying secrets, revisit the as-is authenticated object policy explicitly before implementation rather than introducing silent field loss.
