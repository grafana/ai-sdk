## Decisions

1. **Respect provider-wire versus application history.** V4 provider prompt allows tool-role approval responses but does not allow assistant approval requests. A provider approval request is an output arm with approvalId/toolCallId/metadata. Do not add the root SDK application-level approval-request/signature/isAutomatic shape to the wire prompt or allow providerExecuted on its response. High-level SDK conversion owns application approval history and strips/converts it to V4. Input approved is decoded presence-aware, validated required, then treated as a decision boolean. Retain existing public provider ContentPart.Approved pointer unless an independently reviewed migration is necessary; this is compatibility storage, not optional decision semantics.
2. **Keep execution-denied reason presence.** Independent review selects `ToolResultOutput.Reason *string`: nil is absent, a pointer to empty is explicit empty, and a pointer to text is supplied text. This is the single canonical representation; do not introduce a competing presence flag or legacy fallback field. Migrate repository constructors/readers, document this exported source compatibility change in godoc/change notes, and run affected module tests. Approval-response Reason remains string; synthesis from its normalized empty value produces nil, while nonempty produces a pointer. Native OpenAI, Anthropic, compatible and Bedrock default only when reason is nil. JSON/client boundaries preserve all three states, and capture adapters must intentionally handle nil rather than accidentally changing their documented content shape.
3. **Bounded output lifecycle, no fabricated cross-request state.** Extend existing unary/stream tool state with approval identifiers, correlate emitted requests with known provider-owned tool calls and reject unknown/completed/duplicate conflicting requests safely within existing limits. A response input may contain an approvalId without a serialized assistant approval request: pinned OpenAI explicitly supports that V4 shape and de-duplicates responses by ID. Do not impose an unavailable server session lookup or require approval IDs equal tool-call IDs. Existing root application-history validation remains responsible for local approval correlation. Preserve pending provider-owned historical calls for later results and never run them locally.
4. **Reuse native option and metadata seams.** Map output ProviderOptions only on registered output variants (text/json/error-text/error-json/execution-denied), plus nested text/file result-content ProviderOptions, through mapWireProviderOptions, retaining actual native consumer validation. The `content` output wrapper itself has no registered providerOptions; preserve that boundary. Existing response metadata codec owns limits/UTF-8/opaque object preservation for approval metadata too. OpenAI metadata approvalId and itemId must reach subsequent requests; execution-denied with OpenAI approvalId is suppressed by native conversion when already represented as approval response. Compare exact upstream tests for store true/false and de-duplication, rather than Gateway-specific reinterpretation.
5. **Keep execution at caller/provider boundaries.** Gateway invokes one provider call per HTTP request. Local function approval/execution stays in consumer SDK; hosted MCP approval and execution stay native. Approved, denied and mixed actual-output continuation must exercise both clients, unary and streaming, direct and configured fallback. Existing fallback ordering/eligibility/first-part commitment applies and no approval-triggered replay after output/effects is introduced.
6. **Ownership and files.** AGPL: ai-gateway/providerwire/v4/{request,function_tools,response,stream,stream_tools}.go, focused approval helper/tests as useful, ai-gateway/test/providerwire-v4 request/consumption/runtime/command tests and testserver, ai-gateway/docs capability guide. Apache: provider/types.go (reason), providers/grafana/{request,model,stream}.go and independent tests, native providers' convert_messages/convert_request equivalents where absence defaults or approval conversion differ, root response-history/approval helpers only for demonstrated continuation defects. Root test/integration is needed only if changing frontend-facing core behavior; Gateway contract tests remain under AGPL. OpenSpec governance and PARITY evidence remain neutral documentation.
7. **Evidence before implementation.** Add failing provider-domain presence tests and Gateway/TS client fixtures using deterministic provider-independent mocks or native fake HTTP. Pin request goldens to installed registered clients. Actual follow-up native HTTP bodies, not input snapshots alone, establish continuation. Exercise server and consumer capture independently; capture disabled/enabled must not rewrite responses, and ordinary metadata must survive.
8. **Normalize the real consumer history boundary.** Root `sanitizePromptForProvider` currently retains application-only ProviderExecuted/ToolCallID/ToolName on provider approval responses, whereas Grafana `projectPart` rejects those leftovers. Normalize retained provider approval responses into V4 fields on a copy at the core-to-provider boundary after local ownership/correlation handling; do not weaken the wire union or erase caller-owned history. Exercise Go GenerateText and StreamText actual response-history resume in addition to direct DoGenerate/DoStream transport coverage. TypeScript high-level conversion strips assistant approval requests and local approval responses and currently does not forward approval-response part options; direct V4 client tests establish that registered option scope. Report these evidence layers separately instead of claiming a high-level option path the pinned core does not expose.

The OpenAI continuation witnesses derive `openai.approvalRequestId` from each actual returned approval and attach it to the matching provider-owned call before resuming. This is the registered native adapter's correlation input; neither the registered high-level core nor Gateway synthesizes it. The guide describes this caller step, and the evidence does not claim automatic reconstruction or live hosted MCP acceptance.

## Risks / Trade-offs

- Public reason representation migration touches native providers and root code → select one canonical representation, audit every writer/reader and run all affected module tests; do not leave adapters with empty-string defaults.
- Private Vercel service is unavailable as oracle → claim exact public-client compatibility and native synthetic request evidence only.
- Broad correlation checks can reject legitimate provider-native IDs/truncated history → enforce output lifecycle from available state, preserve native input authority and test standalone registered approval responses.
- Changes shared with other capability work → isolate this worktree and own only approval-related codec switches; source/media #110 remains independent.
- Time pressure → prioritize coherent required acceptance, report gaps explicitly rather than claiming issue closure with only a schema change.

## Migration Plan

No deployment or persistence migration. Commit source and tests together; update public godoc if reason API changes. Do not update baseline pins or release versions. Revert as one capability change if needed.
