# Design

## Context

See proposal.md - Why. Registered baseline: `@ai-sdk/anthropic` 4.0.82 at `b7f6255acaae7724adc0fd37aac3dae3f3466578` (`test/conformance/upstream.yaml`). In `packages/anthropic/src/convert-to-anthropic-prompt.ts` at that SHA, the tool-result `case 'content'` branch handles `data.type === 'reference'` first: `resolveProviderReference({reference, provider: 'anthropic'})`, `betas.add('files-api-2025-04-14')`, then `image` with a `file` source when the top-level media type is `image`, else `document` with a `file` source. There is no `containerUpload` branch and no inner `cache_control`. `resolveProviderReference` returns `reference[provider]` when it is not nullish (so `""` is accepted) and otherwise throws `NoSuchProviderReferenceError`, failing the call. Entries are mapped in order and filtered with `isNonNullable`. Upstream test: `convert-to-anthropic-prompt.test.ts` "should handle tool result with a provider-referenced file" (text/plain reference -> document `file` source, betas `{files-api-2025-04-14}`, no warnings).

Go today (`providers/anthropic/convert_request.go`):
- `convertUserContent` already resolves user-content references through `resolveAnthropicFileReference` (exact `anthropic` key, `""` accepted), returns `anthropic: no provider reference found for provider anthropic; available providers: <sorted>` when the key is missing, adds `filesAPIBeta` with `appendBetaUnique`, and supports `containerUpload`.
- Tool results go `convertUserContent`/`convertToolContent` -> `appendToolResultBlock` -> `serializeToolOutput` -> `convertToolResultFileContent`, none of which return an error. Any file entry that is neither URL nor inline data, including references, returns the `with data type: <arm>` warning.
- `provider.ValidateFileInputs`, called first in `buildParamsWithCapabilities`, already rejects null, malformed, non-string and reserved-`type` references inside tool-result content, so only "structurally valid but no `anthropic` key" reaches the converter.
- `buildParamsWithCapabilities` is shared by the direct provider and Vertex (`vertexProviderCapabilities`). `DoStream` sends each `p.Betas` entry as an `anthropic-beta` header; `DoGenerate` passes `p.Betas` to `Beta.Messages.New`; the `normalizeBetaHeaders` middleware deduplicates header tokens, including caller-supplied headers.
- The synthetic prompt-conversion harness (`test/conformance/testdata/anthropic-prompt-conversion/`, `anthropic_prompt_conversion_test.go`) compares a full Go `DoGenerate` request snapshot, including `anthropic-beta`, and warnings against upstream `doGenerate` output. Its `expected-results.jsonl` was last generated at 4.0.71 (#530) and was not regenerated by the 4.0.82 pin upgrade (#458); the `tool-result-dropped-file-entries` line still expects the reference warning.

## Goals / Non-Goals

**Goals:**
- Executable upstream-oracle evidence that fails before the fix and passes after it.
- One reference-resolution rule shared by user-content and tool-result paths.

**Non-Goals:**
- Live-provider proof that Anthropic or Vertex accepts `file` sources inside `tool_result`; evidence is synthetic request conversion only.
- Media-type classification changes (bare `image`, wildcards); the reference branch reuses the image classification of the URL and inline-data branches. See Upstream differences (3).
- Cache control on inner tool-result blocks, MCP routing and dropped-file warnings (#421).
- Replacing the literal `"files-api-2025-04-14"` in the container-skills branch with `filesAPIBeta`; unrelated to this behavior.

## Decisions

1. **Conformance first through the existing upstream-oracle harness.** Regenerate only the prompt-conversion goldens (`cd test && pnpm --filter @ai-sdk/conformance-tools generate -- --scenario anthropic-prompt-conversion` after `mise deps install --only test`) against the registered 4.0.82 package, and add one synthetic case `tool-result-referenced-files` (labeled `SYNTHETIC:`) covering an `image/png` reference, a `text/plain` reference, empty IDs for an `image/png` and an `application/pdf` entry, and a minimal user-message reference (no filename, provider options or cache control) alongside an inline PDF tool-result entry so the beta set is `files-api` + `pdfs`. The existing `tool-result-dropped-file-entries` case already exercises mixed ordering (text, zip data, reference, text data, URL document, URL image); keep its prompt and update its description. The Go replay must fail before the converter change. Alternative: Go unit tests with hand-written expectations only. Rejected as the primary proof because they are not regenerated on baseline upgrades. The harness runs only `DoGenerate` and its JSON prompts cannot express `provider.BytesDataContent` (JSON data decodes to base64), so unit and native request tests cover streaming, Vertex capabilities, bytes, errors and caller-beta dedup. No `recorded/` or `upstream/` inputs are added: the harness prompts are caller input, not provider events.

2. **Missing `anthropic` key is a conversion error.** Upstream throws for both user and tool-result paths, and the Go user path already errors. Alternative: keep a warning and drop the entry. Rejected: it silently loses the attachment and diverges from upstream and from the Go user path. Alternative: a pre-pass in `buildParamsWithCapabilities` that checks all tool-result references before conversion. Rejected: it splits the rule from the code that emits the block and would need its own traversal of tool outputs.

3. **Thread `error` through the tool-result helpers.** `serializeToolOutput`, `appendToolResultBlock` and `convertToolContent` return `(…, error)`; `convertUserContent` and the `RoleTool` branch of `buildParamsWithCapabilities` propagate it unchanged. `convertToolResultFileContent` keeps returning the warning message for unsupported entries and gains an error for an unresolvable reference. Existing helper callers in tests (`convert_request_test.go`, `denial_presence_test.go`) assert `NoError` for non-reference outputs.

4. **Share the resolver and error text.** Add one small helper (e.g. `resolveAnthropicFileID`) that wraps `resolveAnthropicFileReference` and returns the existing error string; both paths call it, so the user-path message and its tests (`TestBuildParams_ReferencedAnthropicFileRequiresProviderID`) stay byte-identical. Only the user path keeps `useContainerUpload`; the tool-result path has no such option upstream. Block construction stays per path because the SDK union types differ (`BetaContentBlockParamUnion` vs `BetaToolResultBlockParamContentUnion`) and the user path sets cache control. No key normalization: the lookup stays the exact `anthropic` key.

5. **Beta propagation reuses the shared `*betas`.** The reference branch calls `appendBetaUnique(*betas, filesAPIBeta)` (keeping the existing `betas != nil` guard for direct helper calls). Because direct and Vertex share `buildParamsWithCapabilities`, and both `DoGenerate` and `DoStream` read `p.Betas`, no `model.go` change is needed. One table-driven `httptest` test runs every case across `vertex ∈ {false,true}` × `stream ∈ {false,true}` (pattern at `convert_request_test.go:128-160`: `m.capabilities = vertexProviderCapabilities`, captured body and `anthropic-beta` header, request counter). It proves the `tool_result.content` blocks, that `anthropic-beta` contains `files-api-2025-04-14` exactly once when the user path, several tool results and `AnthropicOptions.Betas` all request it, zero requests on conversion errors, and identical content and warnings between unary and stream.

6. **No caller mutation.** The converter reads `ToolResultContentValue` by value and builds new SDK params; tests assert the input prompt is deep-equal before and after conversion.

## Upstream differences

1. **Error type and text** - Go adaptation. Upstream throws `NoSuchProviderReferenceError` (`No provider reference found for provider 'anthropic'. Available providers: <insertion order>`); Go returns the existing lowercase `fmt.Errorf` text with sorted keys, since AGENTS.md forbids custom error types. Both fail the call before any request.
2. **`{"anthropic": null}`** - Go adaptation. Upstream throws from `resolveProviderReference`; Go rejects it earlier in `provider.ValidateFileInputs`. No request is sent either way.
3. **Bare `image` media type (no slash)** - existing implementation gap, owned by open PR #267 ("fix(sdk): handle file input edge cases", which fixes bare `image` for tool-result URLs). Upstream `getTopLevelMediaType` (`provider-utils/src/detect-media-type.ts:364-367` at `b7f6255a`) treats it as an image; the Go `image/` prefix makes it a document. The reference branch must reuse the same image classification as the URL and inline-data branches in `convertToolResultFileContent`, so #267's fix covers all branches; whichever of this change and #267 lands second adopts the other's classification.
4. **Beta order** - Go adaptation. Upstream collects betas in a `Set`; Go keeps append order. The harness normalizes the `anthropic-beta` header, and unit tests assert membership and count.
5. **Live acceptance** - provider-boundary coverage gap. Live Anthropic and Vertex acceptance of `file` sources inside `tool_result`, including `file_id: ""`, is unproven; the PR states this. An optional live check runs through `mise run record-conformance` only if credentials are obtained through the recorder.

## Risks / Trade-offs

- [Behavior change: tool-result references without an `anthropic` key previously dropped with a warning now fail conversion] -> upstream ships it as a fix, the Go user-content path already errors on the same input, and no Go API changes; noted in the proposal and the PR.
- [Regenerating all 12 prompt-conversion cases against 4.0.82 may change cases unrelated to references] -> the generator rewrites every case (no per-case filter, `test/conformance/tools/anthropic-prompt-conversion.mts`). The 4.0.71 (`45e1fbc3`) -> `b7f6255a` diff of `convert-to-anthropic-prompt.ts` adds only the reference branch, a `server-side-fallback-2026-06-01` beta for replayed fallback blocks, and a `tool_search_tool_result` error branch, none used by the 12 cases. If any unrelated line changes, or the MCP fall-through warning disappears (tripping the `require.GreaterOrEqual` check in `anthropic_prompt_conversion_test.go`), stop and escalate; never hand-edit the generated `expected-results.jsonl`.
- [Vertex may not accept Files API sources] -> Go keeps parity with the shared upstream converter (the Vertex Anthropic provider reuses `AnthropicLanguageModel`), as the existing user-content reference path already does; no live Vertex evidence is claimed.
- [Synthetic evidence only] -> request conversion is compared against the upstream oracle; the live-acceptance gap is Upstream differences (5) and is stated in the PR.
