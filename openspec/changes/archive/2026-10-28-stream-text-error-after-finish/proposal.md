# Proposal

## Why

Gateway streams now forward every response segment, so a provider `error` part can arrive after a written `finish`, for example when the stream times out after its last segment. Upstream `streamText` (`ai@7.0.143`) then ends the step with finish reason `error`, while Go `StreamText` keeps the earlier `stop` or `tool-calls`. The TypeScript and Go clients of the same Gateway stream therefore report different finish reasons.

## What Changes

- A provider `error` part sets the step's unified finish reason to `error` and keeps the raw reason of the preceding finish. A later `finish` in the same model call replaces it, so the last terminal part decides.
- The `finish-step` and `finish` stream parts, the UI `finish` chunk and the recorded step carry that reason.
- An error before any finish keeps its current behavior. Tool execution, continuation and tool-choice validation are unchanged.

## Capabilities

### New Capabilities

None.

### Modified Capabilities

- `stream-text-lifecycle`: the step finish reason follows the last terminal part of the model call.

## Impact

- **Code:** `streamtext.go` in the root module.
- **Evidence:**
  - the provider-independent core UI fixture `test/conformance/ui/finish-then-error`, generated by the pinned upstream `streamText`;
  - a cross-language scenario in `test/integration`;
  - a unit test for the raw finish reason.
- **Release:** the root module gets a release through the PR that carries this change.
