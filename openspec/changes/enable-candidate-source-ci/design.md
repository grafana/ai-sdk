## Context

Issue #249 added `go.gateway.work` and selectable public-proxy standalone checks, but explicitly left required gates unchanged. `.github/workflows/ci.yml` currently includes `verify-module-resolution` in the mixed `module-resolution` job and a standalone `image-validation` job. Its publisher needs both, and deployment needs the publisher. `mise.toml` still builds/tests/vets/lints Gateway with `GOWORK=off`; parity ProviderWire Go tests, Gateway command/runtime testservers and the pinned Go-client probe hide additional standalone builds. `scripts/module-policy.sh isolation` removes Gateway source but compiles Grafana against the published SDK root. Root `go.work` must remain SDK-only; the Dockerfile already selects standalone production builds. This is workflow policy work, not a change to the registered Vercel baseline (`test/conformance/upstream.yaml`) or a claim of new parity.

## Goals / Non-Goals

**Goals:** Independently green coordinated source PRs with older merged downloadable internal pins; blocking structural, merged-pin, source behavior and parity checks; visible but nonblocking standalone diagnostics on PRs; exact-revision standalone artifact eligibility before image publication/deployment; deterministic negative-path workflow tests and an approved rollout.

**Non-Goals:** SDK tagging, automatic module release authorization, #245/#21 release-please logic, production workspace substitutions, dependency/license relaxations, upstream or Go runtime behavior changes, settings edits in this proposal.

## Decisions

1. **Split eligibility by purpose, not by `continue-on-error` on a mixed job.** Keep a required source-policy job (preserving `module-resolution` check identity if safe at rollout) for `test-module-policy`, `verify-ai-gateway-boundary`, `verify-merged-pins`, workspace validation and candidate source-absent isolation. Move `verify-module-resolution` out to a distinct, visible nonblocking PR diagnostic. If preserving a job name would orphan a configured required check, obtain approved ruleset/check-name migration before enabling. The diagnostic must not be a dependency of required source aggregation. Alternative: `continue-on-error` on existing `module-resolution` masks provenance failures; rejected.

2. **Make candidate mode explicit on every required Go path.** Root SDK tests/build/lint/vet use root `go.work`; Gateway modules use `go.gateway.work` by explicit absolute path, readonly manifests. Audit all published provider/middleware modules, examples and SDK-only integration server for hidden stale-root compilations; do not implicitly adopt Gateway workspace for the root or examples. Repoint Gateway ProviderWire Go tests, runtime testserver and command test to candidate mode. The required `test-providerwire-v4` path runs `test:contract`, whose `test:client` includes both `go-client-differential.test.ts` and `go-client-request-mutations.test.ts`. Keep the differential assertions and semantic mutation red controls blocking: their Go captures must build and execute the candidate Grafana client with candidate root, not the `GOWORK=off` client currently built by `go-client-capture.ts`. Each red control copies and mutates the client outside the root workspace; supply an explicit temporary workspace/fixture selecting that mutated copy alongside candidate root, verify selection of the copy (not the unmutated client), and prove the resulting failure is a semantic differential `AssertionError`, not a build/setup failure. Preserve genuinely pinned Go-client consumer-contract evidence separately as a visible nonblocking standalone diagnostic or artifact check; do not move the pinned TypeScript comparator, candidate differential suite or red controls out of required parity checks. Conformance's nested `test/conformance/go.mod` uses local replacements despite `GOWORK=off`: retain conformance tests but verify actual selected candidate sources, avoiding an erroneous classification as standalone publication evidence. Alternative: only switch `mise run test-ai-gateway-source` and leave the other required tasks unchanged; rejected because CI still fails on hidden standalone builds.

3. **Preserve isolation and provenance independently.** In a copy without `ai-gateway/`, build/test SDK root and Grafana client against candidate root using an explicit Gateway-free workspace (correct copied absolute paths); verify absence, local source selection and reverse-import/module boundary while preserving declared/selected pin ancestry against canonical `main`. Separate standalone public-proxy validation remains unmodified as a developer and artifact tool, and its missing or unverifiable dependencies fail closed at the artifact gate. Alternative: standalone source-absence validation reintroduces stale-root compilation; rejected.

4. **Tie artifact checks to publication, never source eligibility.** A standalone artifact job validates the exact checkout revision with `MODULE=ai-gateway mise run verify-published-module` (public proxy, clean cache, readonly, `GOWORK=off`, no replacements, including the selected published dependency closure), then validates the standalone multiarch and native image smoke paths already in `image-validation`. All-module standalone validation remains a PR diagnostic and developer command. Preserve the latter as artifact evidence, not a required PR source gate. `publish-ai-gateway-image` on canonical main and `ai-gateway/v*` push must `needs` all required source checks and both successful standalone validation and image validation for that run's `github.sha`; deployment only follows a successful publication of that revision. Use fail-closed `needs` conditions: failure, cancellation or skip never publishes. On PRs, show standalone/image failures as clearly labeled nonblocking diagnostics (e.g. separate PR diagnostic invocation), not a `needs` of the required aggregate; on pushes/tags fail these jobs normally. No workspace path or local `replace` reaches Docker. The Dockerfile builds only the Gateway tree, so an image's revision label represents checkout SHA and its declared published dependencies, *not* candidate source merged in other modules. Alternative: mark the current image job optional globally; rejected because push could publish after failure.

5. **Rollout and proof precede relaxation.** Add deterministic workflow tests for PR/push/tag conditions and `needs` graphs including failed/skipped/cancelled artifact gates; policy fixtures for stale merged pins, unmerged/unverifiable pins, reverse dependencies and source-absent candidate builds; an actual controlled root+provider+Gateway breaking change must pass all required source checks while standalone compilation fails. Confirm the real required-check list with maintainers, secure approval for any ruleset migration, preserve or migrate names atomically and document rollback; do not use bypasses. Require #21 to integrate #245 safeguards before release automation activation, and document manual standalone validation of each selected module pending #245. Alternative: wait for #21 before changing source gates; rejected by #258, whose simultaneous image gate supplies publication protection.

## Risks / Trade-offs

- [PR standalone diagnostic appears green through job-level `continue-on-error`] → Print explicit failing summary/annotation and keep a named separate diagnostic; test failure display and no blocking path.
- [A testserver, client probe or example silently resolves stale pins] → Inventory `go` spawn sites and run a controlled candidate-only source fixture through actual CI commands, not merely `go list` path assertions; mutation fixtures must select and execute the copied mutant and fail on semantics rather than setup.
- [Gateway standalone is ready but other module standalone readiness is not] → Gateway image proof covers declared/published closure at artifact SHA; unrelated SDK publication remains manual selected-module validation until #245/#21.
- [Tag/push source checks skipped or cancellation races publishing] → Strict `needs` and `success()` semantics for required checks and artifact jobs at the same SHA; test event and failure propagation.
- [Ruleset changes orphan a required check] → Capture current configured check identities and obtain explicit maintainer approval prior to coordinated rollout; no repository setting mutation here.

## Migration Plan

1. Implement and test new source/artifact job graph in one independently green PR, preserving old names where compatible; verify PR/merge result and publication failure behavior before relaxing any rule. Coordinate any required-check migration with approved maintainers, not automation bypass.
2. Run controlled coordinated source and negative scenarios on the actual required workflow paths; confirm artifact gate fails for incomplete standalone dependencies on main/tag and succeeds for existing valid artifacts. Do not push or tag to demonstrate this proposal.
3. On rollout, publish an interim maintainer checklist: manually run `MODULE=<root> mise run verify-published-module` before each module publication; update #21 to consume #245 release readiness before enabling automated SDK releases. Roll back workflow/ruleset changes together if source checks lose protection or publication is no longer fail-closed.
