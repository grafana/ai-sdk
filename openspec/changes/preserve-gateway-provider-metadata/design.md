## Context

ProviderWire reconstructs stream events in `ai-gateway/providerwire/v4/stream.go`/`stream_tools.go`, unary output in `response.go`, and strictly validates their JSON schemas; none copies provider-part metadata. `providers/grafana/stream.go` and `model.go` discard it on consumption. `test/conformance/upstream.yaml` pins `ai@7.0.109`, `@ai-sdk/gateway@4.0.88`, provider v4 `4.0.17` and upstream commit `4e8c387622ee1bb0d55841664416d38754d5c9a3`. A local extracted upstream source tree contains `packages/gateway/src/gateway-language-model.ts:69-165`: unary result spreading and pass-through successful SSE events. This does not characterize the private Gateway service. Pinned core `packages/ai/src/generate-text/stream-text.ts:1544-1593,1693` forwards text/tool-call metadata; `parse-tool-call.test.ts:115-155,922-960` asserts provider metadata survives independently of tool metadata. Pinned public Gateway tests in `packages/gateway/src/gateway-language-model.test.ts` exercise unary/stream consumption but do not establish the private service's metadata policy. Direct recorded goldens require `openai.itemId` on text start/end and `anthropic.caller.type=direct` on tool-call and tool-output; the Anthropic second request carries the caller. Current #201 two-client matrix is not in this checkout; #201 describes it at `9518d503` and its independent tool-result mismatches.

## Goals / Non-Goals

**Goals:** Preserve evidence-backed provider continuation metadata on currently supported result parts for both clients, without widening provider capabilities or weakening strict bounds/privacy; compare unchanged direct UI and backend-request goldens.

**Non-Goals:** Arbitrary provider metadata passthrough, private Vercel service parity, broadening supported content (reasoning, provider-defined/executed/dynamic tools), fixing other tool-result request differences, changing caller request projection, or changing recorded provider inputs/direct goldens.

## Decisions

1. **Closed field and placement policy.** Only `providerMetadata.openai.itemId` (nonempty valid UTF-8 string, bounded by the enclosing output budget) and `providerMetadata.anthropic.caller` with exactly `{type:"direct"}` are eligible on text-start/text-end (OpenAI), basic function tool-call/result (OpenAI itemId or Anthropic direct caller), and unary text/tool-call content (same applicable shape). No synthetic `itemId`, no merge from another event. Text-delta, tool-input-start/delta/end, stream-start, response-metadata, errors, finish, and top-level unary metadata are not adopted. For incompatible placement/provider namespace, omit metadata. Reason: the recorded fixtures and provider mapping tests establish these fields; the exposed protocol is intentionally narrower than raw provider metadata. Alternative opaque forwarding (even with byte/depth limits) would expose arbitrary credentials or backend IDs; a single unrestricted provider namespace is not sufficient isolation. At the server boundary, unrecognized namespaces are dropped without parsing or sizing their raw values; even deep, oversized or malformed unknown-namespace values cannot affect supported output because none of their bytes are emitted. Within a recognized namespace, bounded, well-formed, shallow unknown fields are dropped, not errors; review a new field/placement with fixtures and privacy tests before permitting it. Before parsing a recognized namespace, reject its raw bytes if over the remaining output budget, even when it contains only unknown fields. Reject malformed or overly deep recognized namespace JSON (including deep unknown siblings), duplicate keys, and a present approved field with wrong type, unsupported value or unsafe bytes instead of quietly changing meaning. An unsupported value of `anthropic.caller.type` is an invalid approved field, not a future unknown field. Empty projections omit `providerMetadata` altogether. Field-specific rejection never echoes raw values.
2. **Canonical identity and privacy.** Keep the resolver's canonical public `response-metadata.modelId` and omit provider-supplied backend `ModelID`/provider name/response headers; no top-level unary response identity is adopted. These metadata keys must not influence routing, authentication or metadata-only logs/metrics/AO. Tests inject backend IDs, credential-like strings, nested private fields and sensitive headers in *unknown* metadata alongside valid approved fields and assert only approved fields escape. Also inject hostile approved-field strings (e.g. `Authorization: Bearer secret`) to assert malformed identifiers cannot leak: OpenAI text itemId must equal the already-public text block ID on text-start/end, and OpenAI tool-call/result itemId must be a validated provider part identifier with bounded ASCII `[A-Za-z0-9_-]+` shape (no freeform tokens); canonical backend IDs are not inferred from that identifier. A value deliberately disguised as a valid provider item ID cannot be recognized as a secret merely by parsing; this approved provider identifier is intentionally caller-visible, unlike gateway-owned routing/auth fields. No arbitrary values are copied from input `ProviderMetadata` to errors or diagnostics. The accepted direct Anthropic caller constant has no freeform string payload. Alternative: sending any valid string itemId would not meet the basic shape/privacy requirement.
3. **Response-bound validation.** Ignore unrecognized namespace values without parsing, sizing or marshaling them. For each recognized namespace, check raw byte length against the remaining unary or complete SSE-frame limit *before* parsing; only then validate its JSON object and shallow shape (at most namespace -> object -> caller object), rejecting malformed JSON, duplicate keys, deep unknown siblings, unknown nested keys in `caller`, invalid UTF-8/escaping and invalid selected field type or value. Bounded well-formed unknown siblings at the allowed depth are dropped. Budget preflight includes recognized-namespace raw metadata bytes and existing raw output strings, then standard Go JSON encoding and final complete-body/frame length checks enforce actual escaped size. Do not marshal provider-domain structs/maps directly or introduce new unbounded buffers; impose configured `UnaryResponseBytes`/`StreamFrameBytes` as outer maxima and Grafana's existing unary/SSE limits on client consumption. On unary failure write fixed internal error before 200; on stream invalid metadata write no partial frame, cancel provider and attempt at most one safe terminal error (or no extra write on writer failure); preserve existing deadline, bounded drain and body/channel closure. Alternative silent per-field discard for malformed approved fields would hide provider defects and produce incomplete conversation state.
4. **Schema and clients.** Add optional strict `providerMetadata` with finite shape/placement to `ai-gateway/providerwire/v4/schema/{stream_event,unary_success}.json` and matching TS test schema (`ai-gateway/test/providerwire-v4/schema.ts` if applicable). Keep all other events and `additionalProperties:false`. Grafana strict stream allowlist and unary content parser explicitly decode metadata into `provider.StreamPart.ProviderMetadata` / `provider.GenerateContentPart.ProviderMetadata`, with the same accepted shape and limits; retain existing client-owned request/HTTP response and warnings. Unlike server-side provider-domain projection, the Go client rejects unknown keys anywhere inside received `providerMetadata`, including unknown namespaces, unknown recognized-namespace fields and nested `caller` members; retain existing treatment of unknown fields outside `providerMetadata`. Reject malformed or unsupported approved metadata on consumption rather than accepting arbitrary raw JSON. Pinned TS client forwards supplied metadata; verify schema-parsed consumption with the exact pin.
5. **Evidence.** Add focused Go server/client and TS real-handler tests for boundary bytes/escaping, disallowed keys, unsafe identifiers, malformed values, writer/read cancellation, finish/unknown/unary handling and no observability leaks; update only conflicting privacy assertions to reject hostile private fields while retaining required supported metadata. Inspect #201's executable matrix before prescribing its invocation, then replay unchanged `openai/recorded/simple-text` and `anthropic/recorded/tool-call` through both clients and compare UI *and* backend-request goldens. Report metadata equality separately from unrelated tool-result request diffs; do not treat a partial row as passing. Validate direct conformance and provenance; run parity-check and frontend integration for a wire-affecting change. `test/conformance/PARITY.md` remains mixed unless evidence boundary actually changes.

## Risks / Trade-offs

- [Known fields beyond the allowlist remain unavailable] → Review independently against matching pinned fixtures/provider tests, amend contract deliberately rather than implicitly passing arbitrary values.
- [OpenAI itemId is sometimes a different ID from a text block] → Require equality only for start/end text; function calls/results keep their own validated provider item ID; no equality with `toolCallId`.
- [A credential disguised as a valid OpenAI item ID cannot be distinguished from a real provider ID] → Keep provider-controlled identifiers separate from server-owned identity/credentials, constrain public field shape and test that actual gateway secret values in unrelated metadata never escape; do not promise impossible semantic secret detection.
- [Bounded parsing can still allocate proportional to configured limit] → Preflight length before any JSON parse, enforce small fixed shape, serialize only private bounded DTO and final complete-size check.
- [The #201 matrix may be unavailable on this branch and Anthropic still fails for unrelated tool results] → Acquire/merge executable harness before claiming two-client conformance; separate field-level and whole-row outcomes.

## Migration Plan

Ship strict schema/server and Go-client changes together with pinned TS tests and unchanged fixture comparisons; mismatched old Go clients reject new metadata, so do not emit new fields until matching client is distributed/tested in the same rollout. If rollout fails, revert response projection/schemas/client together; existing omission contract and safe error paths remain available. No persisted data migration.

## Open Questions

No new product decision is required for the closed supported-field contract. The location/merge status of #201's executable matrix is an evidence prerequisite for final acceptance, not license to replace it with invented provider fixtures. Expand finish or top-level unary metadata only under a separate, evidence-backed contract change.
