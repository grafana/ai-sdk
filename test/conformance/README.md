# Conformance Tests

Fixture-replay tests that validate the Go SDK produces identical
UIMessageChunk output as the upstream TypeScript SDK for the same
provider API responses. This catches behavioral divergences that
hand-written tests can't anticipate: missing switch cases, dropped
events, wrong field mappings, etc.

## How It Works

1. **Fixtures** are raw provider API responses captured from a real API or
   imported from the matching upstream package, stored as `.chunks.txt` files
   (one JSON event per line, no SSE framing).
2. **Expected output and requests** are generated by replaying each fixture
   through the upstream TypeScript SDK (`streamText` -> `toUIMessageStream`),
   capturing the UIMessageChunk sequence as `expected.jsonl`, and capturing
   provider API request snapshots as `expected-requests.jsonl`.
3. **Go tests** replay the same fixtures through the Go SDK pipeline
   (provider -> `StreamText` -> `ToUIMessageStream`) and compare the
   output chunk-by-chunk and request-by-request against the expected files.

Both SDK outputs use deterministic IDs so fixtures are fully reproducible.
Content block IDs come from the provider, tool call IDs come from the fixture,
and message-level IDs are controlled via `GenerateMessageID`. OpenAI-generated
source IDs are normalized to sequential `src-*` values in TypeScript expectations;
Go OpenAI conformance tests inject the matching deterministic generator.

> [!IMPORTANT]
> Provider fixture inputs are evidence and must never be invented.
> `record-conformance` captures new `recorded/` inputs from a real provider API.
> `generate-conformance` only regenerates expectations from existing inputs; it
> does not record responses, validate provenance, or make hand-authored provider
> events valid conformance fixtures.

## Upstream Parity Baseline

The upstream target for generated expectations is declared in
`test/conformance/upstream.yaml`. That manifest records the Vercel AI SDK
repository, TypeScript package versions, verification commands, and known gaps.
The package versions in the manifest must match every parity TypeScript
consumer under `test/`: conformance tools, integration tests, interop tests, and
CLI tooling.

The current parity coverage map lives in `test/conformance/PARITY.md`. It
classifies each compatibility surface by layer, status, confidence source, and
known gaps. Use it when deciding whether a change needs new fixtures, upstream
source review, or a documented deviation.

Conformance tests are also the preferred regression suite for bugs and features
that cross the provider or UI wire boundary. When a bug can be represented as
recorded provider chunks or provider request snapshots, add or update the
fixture first, confirm the Go replay fails, and then fix the implementation.
For new parity-sensitive features, record or import upstream behavior alongside
the implementation so future baseline upgrades have an executable contract.

## Grafana Provider-Wire Replay

The Grafana conformance package reuses the Anthropic fixture directories
instead of duplicating fixture files. Its fake hosted endpoint accepts
`POST /language-model`, validates provider-wire and auth headers, decodes
the JSON `provider.CallOptions` body, replays the matching Anthropic
fixture through the direct Anthropic provider conversion path, and writes
the resulting `provider.StreamPart` values back as provider-wire SSE with
`providerwire.WriteSSEStreamPart`.

This proves the Grafana provider is a transparent transport boundary: the
`UIMessageChunk` sequence must remain byte-identical to the direct
Anthropic conformance run for the same `expected.jsonl` files.

## Prerequisites

- **Go 1.26+**
- **Node.js 22+** (only for generating/recording expected output)
- **mise**

## Quick Start

```bash
# Validate the registered upstream baseline metadata
mise run validate-parity-baseline

# Run the standard parity check (baseline validation + conformance)
mise run parity-check

# Run conformance tests (uses committed expected.jsonl files)
mise run test-conformance

# Regenerate expected output from existing fixtures; this does not record inputs
mise run generate-conformance

# Run a specific provider test case
cd test/conformance && go test -tags conformance -v -run text-generation ./anthropic/

# Regenerate and run a provider-independent core UI golden
cd test/conformance/tools
pnpm exec tsx ../ui/generated-files/data-and-url/generate.mts
cd .. && go test -run TestUIConformance_ReasoningFiles ./...
```

## Structure

```
test/conformance/
  go.mod                         # separate Go module (imports aisdk + providers)
  upstream.yaml                  # registered upstream parity baseline
  PARITY.md                      # coverage map for parity-sensitive surfaces
  runner.go                      # shared: replay server, config loader, comparison
  tools/                         # TypeScript tooling
    generate.mts                 # regenerate expected.jsonl from fixtures (no API keys)
    record.mts                   # capture new fixtures from real APIs (needs API keys)
    validate-baseline.mts        # validate manifest/package version consistency
    package.json
  ui/                            # provider-independent core UI goldens
    <test-name>/
      input.jsonl                # LanguageModelV4 stream parts
      expected.jsonl             # upstream toUIMessageStream output
      generate.mts               # exact-baseline expectation generator
  <provider>/                    # one directory per provider (e.g. anthropic/)
    conformance_test.go          # Go test file wiring the provider
    upstream/                    # fixtures copied from Vercel SDK
      INDEX.yaml                 # maps upstream fixture names to local directories
      <test-name>/
        config.yaml
        input.chunks.txt
        expected.jsonl
        expected-requests.jsonl
    recorded/                    # unmodified real provider captures
      <test-name>/
        config.yaml              # includes prompt for provenance and re-recording
        input.chunks.txt         # or input-1.chunks.txt, input-2.chunks.txt for multi-step
        expected.jsonl
        expected-requests.jsonl
```

## Fixture Categories

### Core UI

Provider-independent core UI fixtures live under `ui/`. They replay committed
`LanguageModelV4` stream parts through a mock model, compare Go
`StreamText`/`ToUIMessageStream` output with `expected.jsonl`, and include a
fixture-local TypeScript generator that produces the expectation with the
registered upstream `ai` package. Use these fixtures when a core stream or UI
chunk cannot be produced by an existing provider replay without inventing
provider-specific payloads.

### Upstream

Fixtures copied from the Vercel AI SDK test fixtures
(`packages/<provider>/src/__fixtures__/`). These are static — we don't
control the original test scenario, so the fixture files can't be
re-recorded. They can be refreshed by re-copying from the upstream repo.
`mise run parity-coverage` verifies that every mapped provider input remains
byte-identical to the matching fixture at the exact commit recorded in
`upstream.yaml`; it fails when that Git object is unavailable. CI fetches that
commit before running the check.

Each provider's `upstream/` directory has an `INDEX.yaml` that maps
upstream fixture names to local test case directories. Entries with
`null` indicate fixtures that exist upstream but haven't been imported
yet. Update this file when importing new fixtures.

### Recorded

Locally controlled fixtures captured by `record.mts` from real provider APIs.
They have a prompt, configured messages, or UI messages in `config.yaml` for
provenance and re-recording. The recorder stages inputs and expectations before
replacing the previous generated files, and removes stale numbered inputs.
Never hand-author, synthesize, or assemble provider events for a recorded
fixture, including feature, request-conversion, model-capability, error, or
successful response scenarios.

Recorded inputs must remain exactly as captured by the recording tool. Do not
truncate, splice, rewrite, or otherwise derive provider events. Synthetic
responses and transport-failure scenarios belong in focused unit or integration
tests, or in provider-independent `ui/` fixtures when they exercise core stream
behavior.

If live credentials, provider access, or a matching upstream fixture are not
available, use focused unit/integration coverage or remove the provider fixture
and document any remaining provider-boundary gap. Do not substitute synthetic
provider payloads.

Recorded scenarios that need temporary external resources can use environment
placeholders such as `s3://${BEDROCK_S3_BUCKET}/fixture/image.png`. `record.mts`
resolves them only for the live request and restores the placeholder in request
snapshots; raw provider response events are never rewritten.

## config.yaml

Each test case directory has a `config.yaml` with replay metadata.
The provider is inferred from the directory path, not from the YAML.

```yaml
# Minimal streaming fixture
model: claude-sonnet-4-5-20250929

# Non-streaming provider fixture
operation: generate
model: anthropic.claude-3-haiku-20240307-v1:0

# Full (recorded fixture with tools)
model: claude-sonnet-4-5-20250929
system: "You are a tool-using assistant."
prompt: "What's the weather in San Francisco?"
stopWhenStepCount: 2
providerOptions:
  anthropic:
    thinking:
      type: enabled
      budgetTokens: 1024
tools:
  get_weather:
    description: "Get weather for a location"
    needsApproval: true
    inputSchema:
      type: object
      properties:
        location:
          type: string
      required:
        - location
    mockResults:
      - temperature: 72
        conditions: sunny
approval:
  toolCallId: toolu_123
  toolName: get_weather
  approvalId: id-0
  approved: true
  reason: "looks safe"
  input:
    location: San Francisco
```

Fields:
- `operation` (optional, default `stream`): provider operation (`stream` or `generate`); unary `generate` is currently Bedrock-only and supports prompt/configured messages, system text, headers, provider options, and response format
- `model` (required): model ID used for the provider
- `system` (optional): system prompt text passed as a system-role model message
- `prompt` (optional): prompt text; recording requires it unless `messages` or `uiMessages` is configured
- `stopWhenStepCount` (optional, default 1): number of steps for multi-step tool calling
- `toolChoice` (optional): model tool-choice strategy (`auto`, `none`, `required`, or `tool` with `toolName`)
- `activeTools` (optional): list of tool names available for the call
- `streamOptions` (optional): `ToUIMessageStream` options (`sendReasoning`, `sendSources`, `sendFinish`, `sendStart`)
- `providerOptions` (optional): passed through to `StreamText`
- `tools` (optional): function tool definitions with `inputSchema`, mock results consumed in order, or `mockError` for error simulation
- `tools.<name>.needsApproval` (optional): marks a function tool as requiring approval before local execution
- `tools.<name>.providerOptions` (optional): provider-specific options for a function tool
- `providerTools` (optional): provider-defined tools (e.g. `code_execution`, `web_search`) with `id` and optional `args`
- `providerTools.<name>.providerOptions` (optional): provider-specific options for a provider-defined tool
- `responseFormat` (optional): JSON mode config with `type: json` and `schema`
- `assertOutputValue` (optional): requires `expected-object.json` to match the parsed `OutputValue` instead of reconstructed text
- `approval` (optional): seeds a prior tool call, approval request, and approval response for replaying approved/denied second-call flows
- `expectStreamError` (optional): requires the Go replay to end with an error while still comparing emitted UI chunks
- `skipReason` (optional): explicitly skips Go replay for an exact imported fixture that the current provider transport cannot consume; generated upstream expectations and focused replacement coverage remain required
- `maxRetries` (optional): core replay retry count; live recording defaults to zero retries unless this is explicitly set

## Request Input Assertions

Each test case has an `expected-requests.jsonl` file with one request snapshot
per provider API call, in call order. Each line has this shape:

```json
{"method":"POST","path":"/v1/messages","headers":{"anthropic-version":"2023-06-01"},"body":{"model":"claude-..."}}
```

The Go runner captures requests received by the replay server and compares them
against these snapshots after the stream completes.

Comparison rules:
- JSON request bodies are decoded and compared semantically, so object field ordering does not matter.
- Array order remains significant for messages, content blocks, stop sequences, and multi-step request order.
- Tool declaration arrays are sorted by tool name/type before comparison because Go exposes tools as a map.
- Missing fields, extra fields, and different scalar values fail the test.
- Headers are provider-specific allowlists of behavior-affecting headers; volatile transport headers are ignored.
- Anthropic beta header values are normalized as unordered comma-separated sets.
- Secret header values are redacted as `<redacted>` before snapshots are written or compared.
- Anthropic `tool_result` JSON content is compared semantically across SDK serialization shapes.
- Invalid tool-input validator diagnostics are normalized across TypeScript Zod and Go JSON Schema while preserving the tool name and error-result shape.
- Anthropic `web_search_result.page_age: null` is treated the same as an omitted `page_age`.
- Bedrock authenticates via SigV4, so only `content-type` is asserted; `authorization`, `x-amz-*`, `host`, `user-agent`, `content-length`, and `accept` are excluded as volatile or non-behavioral. The request path preserves percent-encoding (model-ID colons become `%3A`) so the captured path matches the upstream `encodeURIComponent` form on the wire.

### Extending config.yaml

When a fixture needs another upstream-visible option, add the YAML field, wire
it through to `StreamText` or `ToUIMessageStream` in `runner.go`, and mirror the
same field in `generate.mts` / `record.mts`.

## Guide: Importing a Test from Upstream

Copy a fixture from the Vercel AI SDK and generate expected output:

### 1. Find the fixture

Browse upstream fixtures:

```bash
ls ../ai/packages/anthropic/src/__fixtures__/*.chunks.txt
```

Pick one. For example, `anthropic-text.chunks.txt` (basic text generation).

### 2. Create the test case directory

```bash
mkdir -p test/conformance/anthropic/upstream/<test-name>
```

### 3. Copy the fixture

```bash
cp ../ai/packages/anthropic/src/__fixtures__/<fixture>.chunks.txt \
   test/conformance/anthropic/upstream/<test-name>/input.chunks.txt
```

For multi-step fixtures (multiple `.chunks.txt` files for the same scenario),
name them `input-1.chunks.txt`, `input-2.chunks.txt`, etc.

### 4. Check the model

```bash
head -1 test/conformance/anthropic/upstream/<test-name>/input.chunks.txt | jq -r '.message.model'
```

### 5. Review the upstream test and write config.yaml

**Important**: before writing the config, find the upstream test that uses
this fixture and check exactly what parameters it passes. The config must
match the upstream test's configuration — otherwise the TS SDK may process
the fixture through a different code path and produce wrong expected output.

Find the test in the upstream source:

```bash
# Search for the fixture name in the test file
grep -n '<fixture-name>' ../ai/packages/anthropic/src/anthropic-messages-language-model.test.ts
```

Check for:
- **Provider tools** (`type: 'provider'`) — add as `providerTools` in config
- **Function tools** — add as `tools` with `inputSchema` and `mockResults`
- **providerOptions** — thinking config, MCP servers, container skills, etc.
- **responseFormat** — JSON mode with schema
- **Multi-step** — whether the test uses `maxSteps` or multiple fixture files

Note: the upstream tests often call `model.doStream()` directly (provider
level), not `streamText()`. Our conformance tests use `streamText()`, so
the config fields map to `streamText` parameters. The key things to match
are tool declarations and provider options, since these affect how the SDK
processes response events (tool name mapping, `dynamic` field, etc.).

Create `test/conformance/anthropic/upstream/<test-name>/config.yaml`:

```yaml
# Minimal
model: <model-from-step-4>

# With provider tools
model: <model-from-step-4>
providerTools:
  code_execution:
    id: anthropic.code_execution_20250825

# With function tools (for multi-step, add mockResults)
model: <model-from-step-4>
tools:
  get_weather:
    description: "Get the weather"
    inputSchema:
      type: object
      properties:
        location:
          type: string
    mockResults:
      - temperature: 72
```

### 6. Generate expected output

```bash
mise run generate-conformance
# or for just this test:
cd test && pnpm --filter @ai-sdk/conformance-tools generate -- --scenario <test-name>
```

This runs the fixture through the upstream TypeScript SDK and writes
`expected.jsonl` plus `expected-requests.jsonl`.

### 7. Update INDEX.yaml

Add the mapping to `test/conformance/<provider>/upstream/INDEX.yaml`:

```yaml
# change from:
<fixture-name>: null
# to:
<fixture-name>: <test-name>
```

### 8. Run the conformance test

```bash
mise run test-conformance
# or for just this test:
cd test/conformance && go test -tags conformance -v -run <test-name> ./anthropic/
```

### 9. Interpret results

- **PASS**: the Go SDK produces identical output to the TypeScript SDK
  for this fixture.
- **FAIL with diff**: the Go SDK diverges. The diff shows exactly which
  chunk differs and what the expected vs actual values are. This is
  either a bug in the Go SDK or a known intentional difference.

## Guide: Recording a New Test Case

Capture a fixture from a real provider API. This is the only way to create a new
successful provider fixture under `recorded/`; do not create `input.chunks.txt`
by hand or with `generate-conformance`:

### 1. Create config.yaml

```bash
mkdir -p test/conformance/anthropic/recorded/<test-name>
```

Write `config.yaml` with `prompt` (required for recording):

```yaml
model: claude-sonnet-4-5-20250929
prompt: "Explain quicksort in one sentence"
```

### 2. Set API key

```bash
export ANTHROPIC_API_KEY=sk-ant-...
```

### 3. Run the recording tool

```bash
SCENARIO=<test-name> mise run record-conformance
```

This makes a real API call, captures the response as `input.chunks.txt`,
and generates `expected.jsonl` plus redacted `expected-requests.jsonl` from
the same run.

### 4. Run the conformance test

```bash
mise run test-conformance
```

## Adding a New Provider

1. Create the provider directory:
   ```bash
   mkdir -p test/conformance/<provider>/upstream test/conformance/<provider>/recorded
   ```

2. Write `test/conformance/<provider>/conformance_test.go` following the
   pattern in `test/conformance/anthropic/conformance_test.go`:
   - Import the provider package
   - Implement a `ProviderFactory` that creates the provider with a
     custom base URL pointing at the replay server
   - Call `conformance.DiscoverTestCases` and `conformance.RunTestCase`

3. Add the provider to `createModel()` in `tools/generate.mts` and
   `tools/record.mts`.

4. Add provider base URL to `PROVIDER_BASE_URLS` in `tools/record.mts`.

5. Add the provider's request-header allowlist in **both**
   `runner.go` (`requestHeaderAllowlists`) and `tools/common.mts`
   (`providerHeaderAllowlists`). The two allowlists MUST agree or the
   request-header comparison will diverge.

6. Copy/record fixtures and generate expected output as described above.

### OpenAI notes

The OpenAI provider lives at `test/conformance/openai/`. The Go factory appends
`/v1` to the replay base URL because upstream `createOpenAI({ baseURL })` and the
openai-go SDK both target `/v1/responses`. The pinned upstream `createOpenAI` factory does not expose its internal source ID
generator, so generated and recorded TypeScript expectations normalize source IDs.
Go replay wires the matching deterministic generator via `openai.WithGenerateID`.
Recording requires `OPENAI_API_KEY`:

```bash
SCENARIO=openai/recorded/<name> mise run record-conformance # record one case
mise run generate-conformance                               # regenerate goldens (no key)
```

Recorded coverage (`openai/recorded/`): `simple-text`, `tool-call`,
`parallel-tool-calls`, `multi-tool-chain`, `reasoning-text`,
`reasoning-tool-use`, `web-search`, `code-interpreter`, `structured-json-output`.

Recording caveats:

- **Zero Data Retention (ZDR) orgs**: multi-turn cases must set
  `providerOptions.openai.store: false` so prior items are re-sent inline rather
  than referenced by id (ZDR orgs do not persist items, so `item_reference`
  fails). Reasoning round-trips additionally rely on
  `include: ["reasoning.encrypted_content"]`, which the provider auto-populates
  when `store` is false.
- **`previous_response_id` continuation** cannot be recorded on a ZDR org (it
  requires server-side storage); it remains covered by focused provider unit
  tests rather than a recorded fixture.
- **MCP tool-approval** requires a live remote MCP server; pinned upstream MCP
  approval fixtures provide provider input, with focused request/response unit
  tests covering additional edge cases.
- Normalization: `function_call_output.output` carries the tool result as a JSON
  string; both the Go runner and `common.mts` parse it so object field ordering
  is compared insensitively.

## Relationship to Other Test Layers

| Layer | What it tests | How |
|---|---|---|
| Unit tests (Go) | Internal logic, type conversions | Hand-written mocks, testify |
| E2E tests (Go) | Full StreamText-to-SSE pipeline | httptest + mock models |
| Integration tests (Go + TS) | Wire compatibility with @ai-sdk/react | Go server + TypeScript Vitest |
| **Conformance tests** | **Behavioral equivalence with TypeScript SDK** | **Fixture replay + exact comparison** |
